1) QUE ES
Un deposito y 3 locales de ropa (Zelarrayan, White, San Lorenzo). Mas de 100 ventas por dia por local. Se carga mercaderia en el deposito, se imprimen etiquetas con codigo de barras, se reparte a los locales (cada local confirma la recepcion), se vende escaneando, se cobra con 3 medios de pago, se imprime ticket, y se hacen devoluciones con nota de credito.

Stack: Next.js 16 (App Router, Turbopack, React 19, server actions), TypeScript, Postgres 17 en un VPS (Easypanel), librerias: pg, jsbarcode, qrcode.react, pdf-lib. IMPORTANTE: esta version de Next tiene cambios (por ejemplo "middleware" se llama "proxy"). Leer la guia en app/node_modules/next/dist/docs/ antes de usar una API de Next.

Ruta del proyecto: carpeta raiz con dos partes: app/ (la aplicacion) y db/ (scripts SQL numerados). Repositorio privado en GitHub: kevinmontesino-sudo/sistema-stock.

4) REGLAS DE NEGOCIO (no cambiar sin que Kevin lo decida)
- Precio de lista = precio con transferencia. Efectivo = lista menos 20%. Tarjeta = lista mas 20%.
- Pago mixto: primero lo que el cliente entrega en un medio (monto), el resto con el segundo medio. El efectivo que entrega cubre lista = monto / 0,8.
- SKU por modelo (nombre + precio de lista). Mismo nombre y precio = mismo SKU (recarga de stock). La fecha "ing dd/mm" es solo interna.
- Solo se vende lo que hay en el stock del local elegido. El stock que va "en camino" no se puede vender hasta que el local lo recibe.
- La nota de credito vale lo que el cliente pago por esas prendas (con el ajuste del medio). Al usarla cubre monto / (1 + ajuste) del valor de lista. No vence. Se devuelve hasta 15 dias despues de la compra. Solo vale (no efectivo). Falladas no vuelven al stock.
- Ticket interno, no fiscal (ARCA mas adelante). Etiquetas 50x30 mm, ticket 80 mm.
- Promos (3x2 siempre sobre precio de lista, a veces acumulables; 2x1; descuentos por promo): PENDIENTES. Las crea y activa solo un administrador desde un panel. La venta ya tiene el campo descuento_promo.
- Ventas por telefono en el Deposito: PENDIENTE de definir con Kevin (cobro, entrega, reserva de stock, estados del pedido).


5) SEGURIDAD: COMO ESTA ARMADA (no romper)
- app/proxy.ts: primera barrera, sin cookie solo se ve /login. Las server actions pasan (ellas mismas rechazan).
- app/lib/seguridad/: clave.ts (scrypt), totp.ts (TOTP RFC 6238 + cifrado AES-256-GCM con APP_KEY), sesion.ts (sesiones en la tabla sesiones; cookie httpOnly; admins 8 h / 2 h de inactividad, resto 14 h / 6 h), permisos.ts (ROLES y matriz PERMISOS: es el UNICO lugar donde se ajustan los permisos), contexto.ts (usuario de la accion en curso, para auditoria y registros), auditoria.ts, limite.ts (5 fallos por usuario o 30 por IP en 15 min), guardia.ts (guardia de pantallas).
- app/app/actions.ts: TODA accion pasa por seguro(permiso, fn) y usa suc(u, sucursal) para forzar la sucursal del usuario. Toda accion nueva DEBE hacer lo mismo. Nunca confiar en un dato que mande el navegador (sucursal, rol, usuario).
- Cada seccion tiene un layout.tsx con requerirPermiso(...). /admin/* solo administradores.
- Roles: admin (Kevin y Cesar), encargado (jefe de un local), vendedor (cajero de un local), deposito. Sucursal: vendedor y encargado quedan fijos en su local; deposito en el Deposito; admin elige.
- Base de datos: triggers que impiden UPDATE, DELETE y TRUNCATE sobre ventas, venta_items, venta_pagos, nota_credito_items, movimientos, cargas y auditoria; en notas_credito solo se puede bajar el saldo. Solo se saltean con SET LOCAL app.mantenimiento = 'on' (uso manual y excepcional, por ejemplo limpiar datos de prueba). Los pagos de ventas, la auditoria y el historial nunca se modifican desde la app.
- Auditoria: tabla auditoria (solo se agrega). Se registra: login, fallos, bloqueos, 2FA, cambios de clave, usuarios, cargas, envios, notas emitidas, cambios de precio, ajustes de stock, bajas, accesos denegados.
- Contrasenas: minimo 10 caracteres y 3 tipos de caracteres. Las que crea un administrador son temporales (se muestran una sola vez y obligan a cambiarlas).
- Cabeceras de seguridad y CSP en app/next.config.ts. npm audit: 0 vulnerabilidades.
- Pendiente de seguridad: aplicar db/010_usuario_web.sql con un superusuario y usar el usuario stock_web en produccion; cerrar el puerto 5432 al publicar; HTTPS; copias de seguridad automaticas fuera del servidor con prueba de restauracion; CSP con nonce (mejora); allowedOrigins de las server actions con el dominio final.
